# 실용성·사업성 불확실성 축소를 위한 검증 요구사항 v0.3

- 대상 저장소: mukgore/codex
- 기준 증거: 728525c4d3e81142f1d916a8a58205c7fb36d977 및 작성 중 추가된 main 5d94e58b3d60aa8c2b2079b0dc022e9d511be7f8의 2026-10-26 보충 보고서
- 문서 상태: 후속 검증 설계. 별도 표준 채점 실험 모듈의 합성 테스트만 시작했으며 실제 성능 검증 결과는 아니다.
- 이번 요청의 승인 범위: 명세 작성 및 GitHub 커밋, 추가 지시에 따른 handcaptcha prod 코드 분석과 별도 표준 채점 모듈 개선 시작. 이 범위에서 합성 데이터 단위 검사를 수행한다. 신규 참여자 모집·기업 연락·유료 서비스 구매·외부 배포 승인을 뜻하지 않는다.
- 기존 인간 데이터 분석 v0.2를 대체하지 않는다. 기존 F1–F4 실험 카드를 실행 가능한 검증 항목으로 구체화하고 사용성·경제성·구매 검증을 연결한다.
- 아래 수량과 임계값 중 “탐색 기본안”은 실행 계획을 구체화하기 위한 제안이며, 이미 합의된 성능 목표나 업계 표준이 아니다.

## 1. 쉬운 설명

이 연구는 “사람은 따라 할 수 있지만 로봇은 따라 하기 어려운 손동작 시험”을 만드는 일이다.
시험을 팔려면 다음을 각각 확인해야 한다.

1. 채점 선생님이 틀린 답에도 합격을 주지는 않는가?
2. 로봇이 답안집을 외워서 통과한 것은 아닌가? 처음 보는 문제에서도 시험해 보는가?
3. 카메라 문지기를 붙였을 때, 손을 가리는 시험이 실제로 도움을 더 주는가?
4. 진짜 사람도 너무 어렵거나 귀찮아서 떠나지는 않는가?
5. 운영하는 데 아끼는 돈보다 더 많은 돈과 시간이 들지는 않는가?
6. 필요한 회사가 실제로 자기 돈을 내려고 하는가?

한 시험에서 잘 나와도 다른 시험의 합격을 대신하지 못한다. 실패 원인을 찾는 것도 검증의 정상적인 결과다.

## 2. 목표, 비목표 및 현재 출발점

### 2.1 목표

- 가림 CAPTCHA의 추가 보안 효과, 정상 사용자 부담, 반복 공격 비용, 운영 비용 및 실제 구매 필요성을 분리해 판정한다.
- “새로운 보안 제품 개발 지속 / 특정 고객과 제한적 공동평가 / 설계 수정 후 재검증 / 다른 용도 탐색 / 판단 보류” 중 하나를 근거와 함께 선택한다.
- AI가 긍정적인 결론을 만들기 위해 데이터·분모·기준을 바꾸지 못하도록 실행 전 계약을 고정한다.

### 2.2 비목표

- 재현성 일치만으로 보안성 입증, 사람 신원 확인 또는 업계 인증을 주장하지 않는다.
- 기존 약 10시간 HaMeR 실행 기억을 검증된 공격 비용으로 사용하지 않는다.
- 모든 가상 카메라를 차단하거나 모든 AI 공격을 방어한다는 목표를 세우지 않는다.
- 이 명세만으로 유료 제품 출시, 특허 유효성, 개인정보 관련 법적 판단을 확정하지 않는다.
- 외부 사이트 공격, 실제 사용자 차단, 자동 기업 연락은 범위 밖이다.

### 2.3 기존 증거를 다시 실험하라고 오인하지 말 것

| 증거 | 확인한 내용 | 이번 검증에서의 역할 |
|---|---|---|
| 기존 38개 기록 재현 | 후보 코드와 기준 좌표에 조건부로 저장 점수 재현 | 과거 계산 회귀 기준. 새 실사용 성능 표본이 아님 |
| A/B 10명 | 재생 영상 대 정적/keyframe 제시의 차이 | 가림 유무 또는 입력 보호 효과로 해석하지 않음 |
| 인간 18세션 | 점수 기준 17/18 통과 | 기존 코호트 기술통계. 새 인간/공격자 대응 비교로 합치지 않음 |
| HaMeR 28조합 | 점수 28/28, 전체 관문 성공 조합 10/28 | 점수와 관문 구분. 실제 보호 동작 성공률이 아님 |
| 고정 원 비교 | 좌표 주입 양쪽 8/8, 합성 손 재검출 양쪽 5/8 점수 통과 | 이미 수행된 비교. 고정 원 효과 입증으로 쓰지 않음 |
| 피부-bit 식별 | top-1 14/16, 저장 궤적 점수 16/16 통과 | 기존 8개 원동작을 공유하는 closed-set 결과 |
| 오인식 궤적 | 두 오인식 방향도 0.854652로 점수 통과 | V1의 필수 회귀 사례. 원 궤적만의 공격이라고 바꾸어 부르지 않음 |

추가 확인(2026-10-26): 기존 8개 source의 pixel extraction이 8/8 재현됐다. 과거 네 후보 지표도 별도 4세션×9 trial 코호트에서 정의·독립 재생 근거가 회수됐다. 이를 prod18 실행 증거나 신규 held-out으로 합치지 않는다. 로컬 후보 HTML의 정적 확인에서도 L3 보호 endpoint 실증은 확보되지 않았다. 따라서 이미 해결된 추출 재현이나 후보 정의 회수를 새 필수 과제로 반복하지 않는다.

과거 고정 원 비교는 손 크기·좌표까지 달라 원 정보의 인과효과를 분리하지 못했다.
기존 결과를 수정·삭제하지 않고 새 run_id 아래 결과를 만든다.

## 3. 요구사항 상태 및 판정 규칙

모든 요구사항에 status, evidence_path, limitation, next_action, owner_role을 기록한다.

- NOT_STARTED: 아직 착수하지 않음.
- READY: 입력·코드·프로토콜이 준비됨.
- BLOCKED: 필수 자료·장치·권한·실행 범위가 없어 수행 불가.
- COMPLETE: 지정된 검증을 수행하고 검산 및 보고를 마침. 효과가 좋다는 뜻이 아님.

별도 outcome은 SUPPORTED / REFUTED / INCONCLUSIVE / NOT_TESTED 중 하나다.
“공격 성공을 찾았다”는 COMPLETE + REFUTED가 될 수 있다.
실행하지 않은 항목에 0% 공격 성공률을 채워 넣지 않는다.

각 실험의 계약에는 다음 항목이 반드시 있어야 한다.

- 가설, 비교 조건, 주 지표 하나, 보조 지표, 분석 단위와 분모
- 사용 데이터와 source 분할, 코드·의존성·설정 버전, 공격자가 아는 정보
- 사람·공격자의 시간 제한과 재시도, 자원 한도, 제외 사유
- 효과의 방향과 최소 의미 있는 차이, 허용 가능한 사람 부담
- 필요한 표본 정밀도/검정력과 근거 또는 “탐색 연구” 명시
- 진행·중단·판단 보류 기준, 실행 범위의 승인 근거

목표값이 비어 있어도 탐색 기술통계는 만들 수 있지만, 확증 성능 합격 판정은 BLOCKED다.
테스트 결과를 본 뒤 목표를 정하면 새로운 protocol_version과 새로운 미사용 시험 집합이 필요하다.

## 4. 공통 기반 요구사항 (V0)

### V0-01 자료 계보 및 재현성

- 기존 원본은 읽기 전용으로 취급하고 작업본·출력을 분리한다.
- protocol_version, code_commit, dirty_diff_hash, scoring_version, challenge_manifest_version,
  input_protection_version, dependency_lock_hash, seed, hardware, browser, OS를 기록한다.
- 자료가 비공개 로컬 경로에만 있으면 로컬 참조 ID를 사용한다. 개인 경로·입력 해시·참여자 식별자는 공개하지 않는다.
- 과거 실행 빌드 미확정을 새 실행 기록으로 소급 해결했다고 쓰지 않는다.
- 생성기, 채점기, 공격 설정을 잠근 뒤 평가한다. 변경 시 새 실행으로 구분한다.

수용 기준: 필수 메타데이터 누락을 검사하는 검증기가 작동하고, 공개 집계가 비공개 원자료로 추적 가능하다.

### V0-02 평가 층 분리

- L1: 문제 식별·손 좌표 추정. top-1, 검출률, 관절오차 등.
- L2: 좌표/영상에서 관문 및 점수 통과. 입력 출처를 보증하지 않음.
- L3: 새 challenge 발급부터 서버가 보호된 테스트 동작을 허용하기까지의 전체 경로.

L2 좌표 주입은 진단 채널이다. 실제 카메라 공격의 L3 성공으로 합산하지 않는다.
전체 성공은 서버 기록의 protected_action_allowed=true로 판정한다.
서버 또는 입력 보호가 없으면 해당 L3 조건은 NOT_TESTED이며 가정으로 메우지 않는다.

### V0-03 최소 실행 로그

비공개 attempts.jsonl의 각 행은 최소 아래 필드를 포함한다.

| 영역 | 필드 |
|---|---|
| 식별 | run_id, protocol_version, attempt_id, session_id, pseudonymous_actor_id |
| 문제 | challenge_id, source_group_ids, split, condition_id, capture_group_id |
| 주체 | human_or_attack, attack_family, input_channel, attacker_knowledge |
| 버전 | code_commit, dirty_diff_hash, scoring_version, protection_version, manifest_version |
| 시간 | challenge_shown, permission_requested, permission_resolved, recording_started, submitted, server_decided |
| 판정 | input_integrity_pass, gate_pass, score_pass, token_valid, protected_action_allowed |
| 수치 | raw_metrics, normalized_metrics, final_score, detection_rate, retry_index |
| 실패 분류 | terminal_status, failure_stage, failure_reason, timeout, log_complete |
| 비용 | setup_wall_ms, online_wall_ms, cpu_time_ms, peak_memory_mb, bytes_uploaded, bytes_downloaded |

- 시간은 단조 시계 기반 경과시간으로 기록하며 서버·클라이언트 원시 시각을 직접 빼지 않는다. 시계 간 대응이 필요한 경우 왕복 측정과 오차를 별도 기록한다.
- final_score가 없으면 null과 이유를 쓴다. 입력 보호를 수행하지 않으면 input_integrity_pass=null이다.
- 중단된 세션도 보존한다. 전체 경로 시간은 화면 제시부터 서버 결론까지, 권한 요청 시간은 별도 포함/분리 보고한다.
- 프레임 계측은 global_frame_id, monotonic_timestamp_ms, phase_before, phase_after, detection_status를 기록한다.
- 기존 accel은 시간 단위 물리 가속도가 아닌 좌표 이차 차분임을 유지한다. 시간 보정판은 별도 버전이다.
- 원영상은 기본적으로 새로 저장하지 않는다. 픽셀 분석에 꼭 필요할 때만 별도 동의·보관기간·삭제 절차를 정한다.

### V0-04 분석 분모

- 인간 첫 시도 성공률 = 첫 시도 전체 성공 세션 / challenge가 제시된 배정 세션.
- 재시도 포함 성공률 = 정해진 시도 한도 내 성공 세션 / challenge가 제시된 배정 세션.
- 공격 성공률 = 보호 동작 성공 공격 시도 / 유효 challenge에 대해 시작된 공격 시도.
- 공격 프로그램 오류·추출 실패·timeout도 분모에 남기고 사유별 제시한다.
- 확인된 실험 장비 장애는 사전 규칙으로 전체 분모와 별도 기술분모를 함께 제시한다. 실패만 임의 제외하지 않는다.
- 로그가 없어 성공 여부를 모르면 missing으로 두고, 결측 전부 실패/전부 성공 경계값을 병기한다.
- 프레임 수, 같은 원본의 역재생·조합 수를 독립 표본 수로 사용하지 않는다.

## 5. V1 — 채점기가 틀린 답을 거부하는가? (최우선)

### V1-01 가설

현재 점수·관문 체계가 정답 재현과 잘못된 동작을 구분하는지 확인한다.
“계산이 정확하다”와 “판별이 타당하다”를 별도 검증한다.

### V1-02 입력과 대조군

같은 목표 challenge별로 아래 응답을 평가한다.

1. 양성 제어: 기준 궤적을 명세된 방향·정규화에 맞춰 넣은 진단용 oracle 응답.
2. 정상 응답: 같은 목표를 실제로 수행한 사람 기록. 연결이 입증되지 않은 과거 기록은 제외가 아니라 별도 코호트로 보존.
3. 다른 동작: 다른 source의 정상 궤적을 잘못된 목표에 제출.
4. 쉬운 오답: 정지 자세, 첫 자세 유지, 마지막 자세 유지, 시간 역전, 구간 순서 변경.
5. 기존 G4 오인식 궤적 두 건: 식별 실패에도 점수 통과한 회귀 사례.
6. 판정 무결성: null, 비유한 값, 빈 배열, 너무 짧은 기록을 정상 합격으로 처리하는지.

oracle은 실제 사람 표본이나 실서비스 공격 성공으로 세지 않는다.
N개 source의 다른 동작 비교는 방향 있는 N(N-1)쌍을 평가하되 독립 N(N-1)개로 추론하지 않는다.

### V1-03 절차

- 기존 scoring_version을 변경하지 않고 score_pass와 gate_pass를 각각 산출한다.
- 목표×응답 confusion table 및 오답 유형별 점수 분포를 만든다.
- 잘못된 동작 중 유사 동작/명확한 오답을 결과를 보기 전에 라벨링한다.
- 임계값·가중치·정규화 개선 후보는 dev에서만 조정하고 val에서 후보 하나를 선택한다.
- 기존 0.25 및 기존 관문은 회귀 비교에 유지한다. 후보판을 기존판 결과로 덮어쓰지 않는다.
- test에서는 잠근 임계값의 결과만 주 분석으로 사용한다. test의 최적 cutoff는 사후 탐색으로만 표시한다.

### V1-04 산출 및 판단

- 산출: wrong_answer_summary, confusion_matrix, scorer_regression, threshold_selection_record.
- 완수 기준: 모든 오답 종류의 수행/차단 사유, 목표별 분모, 점수·관문 별 결과, 회귀 사례의 결과가 있음.
- 중단 기준: 정상 oracle이 규약대로 동작하지 않거나 입력 파서가 invalid를 합격시키면 먼저 구현 오류를 해결한다.
- 현재 후보의 명확한 오답이 반복 통과하면 “채점 판별 문제”로 기록한다. 관문이 막았으면 점수 취약과 전체 실패를 구분한다.
- 확증 합격은 실행 전 정한 인간 통과 하한과 오답 통과 상한을 동시에 만족해야 한다.
- 인간 자료가 부족하면 “오답 취약성 검토 완료, 사람 허용오차 검증 미완료”로 종료할 수 있다.

## 6. V2 — 새 문제에서도 저비용 공격을 막는가?

### V2-01 데이터 분할

- 분할 단위는 원본 source 및 동일 촬영에서 나온 capture_group이다.
- 동일 원본의 crop, mirror, reverse, 시간 변형, mask 변형은 같은 split에 둔다.
- 두 source를 조합한 challenge는 양쪽 source가 같은 split에 있을 때만 사용한다.
- dev / val / test manifest를 고정하고 교집합 0을 자동 검사한다.
- 촬영자/손 모양/배경 일반화를 주장하려면 해당 capture identity도 test에서 분리한다. 동작 source만 분리했으면 그 범위만 주장한다.
- 기존 8개 원본은 이미 관찰했으므로 그 안의 재분할을 “완전히 새로운 미관찰 test”라고 부르지 않는다.
- 새로운 자료가 없으면 existing_closed_set 결과까지만 완료하고 held-out은 BLOCKED로 남긴다.

탐색 기본안: 새 source 30개를 dev 12 / val 6 / test 12로 분리한다.
이는 확증 표본이 아니며 촬영 그룹 분리로 수량이 바뀌면 실행 전에 manifest를 수정한다.
작은 test에서 실패를 못 찾았다는 이유로 낮은 실제 공격률을 보증하지 않는다.

### V2-02 공격군 및 지식 수준

| 공격군 | 사용하는 정보 | 필수 기록 |
|---|---|---|
| A0 간단 응답 | 정지·평균 자세, 소수 프레임 보간 | 프레임 수, 준비·질의 비용 |
| A1 일반 인식 | 공개된 가림 영상에 대한 MediaPipe 등 고정 구현 | 버전·설정·실패 프레임 |
| A2 원 정보 | 중심·반지름의 시간열만 | 원 정보 추출 경로, 다른 픽셀 사용 여부 |
| A3 피부-bit | 경계 가시성 패턴과 참조 라이브러리 | 라이브러리 출처·크기·구축 비용 |
| A4 메타데이터 | 공개 파일명·길이·URL·전환 패턴 | 실제 공개 범위와 입력 목록 |
| A5 복원/합성 | 사용 가능한 복원기와 렌더 후 재검출 | 모델·가중치·장비·실행 경로 |

A2와 A3를 같은 공격으로 합치지 않는다. 원정보 oracle을 제공했다면 실제 픽셀 추출 공격과 구분한다.
A5는 로컬 CPU/무료 자원에서 실행 가능한 범위만 실시한다. 미실행을 방어 성공으로 취급하지 않는다.

- K0: 코드와 공개 challenge만 알고 비공개 test 정답은 모름.
- K1: 공개된 dev/val 원본 및 준비 단계에 허용된 자료로 만든 사전 라이브러리를 가짐.
- K2: test 정답 라이브러리 제공. 누출/상한 진단 전용이며 미관찰 일반화 주장 금지.
- 새로운 문제의 정답을 미리 라이브러리에 넣은 뒤 K0/K1이라고 표기하면 해당 run은 무효다.
- test 피드백으로 공격을 수정하면 새 test가 필요하다. 고정 풀에서 반복 노출로 학습하는 실험은 별도 adaptive 시나리오다.

### V2-03 공정한 비교와 누출 분리

- 동일 source 영상으로 무가림과 가림을 생성한다. 해상도·손 크기·좌표·재생시간·전환·코덱 등은 가능한 한 동일하게 유지한다.
- 바뀐 변수를 전부 기록한다. 여러 변수가 함께 바뀌면 가림 단독의 인과효과라고 쓰지 않는다.
- 가림의 움직임/크기 누출을 분리하는 ablation은 한 번에 한 요소만 바꾼다.
- 공격별 동일한 질의·재시도·CPU 예산을 적용하고 budget을 manifest에 명시한다.
- 속도 변형/색상 변형만으로 문제 공간이 충분히 새로워졌다고 가정하지 않는다.

### V2-04 산출 및 판단

- source별 L1 식별, L2 관문·점수, 가능한 경우 L3 전체 성공을 각각 보고한다.
- 기존 closed-set, 새 held-out, 반복 노출 adaptive 결과를 다른 표에 둔다.
- 적어도 하나의 저비용 공격이 목표 상한을 넘으면 해당 위협 모델에서 현재 후보를 REFUTED로 판정한다.
- 모든 시험 공격이 실패해도 “시험한 공격과 예산 내 결과”로만 결론 낸다.
- 관련 공격군이 BLOCKED면 포괄적 보안 우위는 INCONCLUSIVE다.

## 7. V3 — 입력 보호와 결합할 때 가림의 추가 효과가 있는가?

### V3-01 조건 설계

가능한 범위에서 2×3 조건을 비교한다.

| 조건 | 입력 보호 | 손동작 과제 |
|---|---|---|
| P0 | 없음 | 없음 |
| P1 | 있음 | 없음 |
| U0 | 없음 | 무가림 모방 |
| U1 | 있음 | 무가림 모방 |
| O0 | 없음 | 가림 모방 |
| O1 | 있음 | 가림 모방 |

- 주 비교: O1 대 U1. 입력 보호가 같은 상태에서 가림의 추가 효과.
- 보조 비교: O1 대 P1. 입력 보호만으로 충분한지.
- 입력 보호 기여: O1 대 O0, U1 대 U0.
- P 조건은 보호 도구가 단독으로 완결된 판정을 제공할 때만 사용한다.
- 얼굴 입력이 필수인 도구를 손 입력으로 대체해도 유효하다고 가정하지 않는다. 비교 불가능하면 P 또는 보호 조건을 BLOCKED로 두고 이유를 쓴다.
- protection stub/mock은 통합 테스트 전용이다. 실제 방어 효과에 포함하지 않는다.

### V3-02 입력 보호 적합성 조사

도구별 문서와 실제 지원 범위로 다음을 확인한다.

- 손 영상/외부 challenge 허용 여부
- 보호된 캡처와 세션 challenge를 연결할 수 있는지
- 브라우저·OS·장치 지원, SDK·서버 의존성
- 출력이 위험 신호인지, 서명 검증 가능한 증명인지
- 가격·시험판·라이선스·데이터 전송 조건
- 실제 시험 가능한 공격 종류

카메라 이름 차단은 약한 휴리스틱 별도 조건으로 표시한다.
물리 카메라 사용 또는 모든 영상 주입 방지를 증명한 것으로 쓰지 않는다.
무료로 적합한 도구를 확보하지 못하면 통합 적합성 조사까지만 완료한다.

### V3-03 통제된 전체 경로 시험

사용자 소유 로컬/비공개 테스트 시스템에서만 다음을 시험한다.

- 정상 카메라 입력
- 허용된 시험용 가상 카메라/녹화 입력
- 클라이언트 passed/score 변조 또는 보호 API 직접 호출
- 만료·재사용·다른 세션의 인증 결과 제출
- 누락·오염된 서버 검증 입력

서버는 클라이언트 passed 값만으로 허용하지 않는다.
challenge/session/action을 연결하고 만료와 일회성 소비를 검증한다.
정답 reference·서명키를 클라이언트에 제공하면 그 노출을 위협 모델에 포함한다.
서버 점수 재계산만으로 영상 출처의 진실성을 보증했다고 하지 않는다.

### V3-04 판정

- 보호 동작 성공 여부를 서버 로그에서 검산한다.
- 프로토콜 우회가 한 번이라도 재현되면 그 경로의 제품화 준비는 실패로 표시하고 수정 후 동일 회귀 시험을 실시한다.
- O1의 공격 성공 감소와 정상 사용자 부담 증가를 함께 비교한다.
- 입력 보호만으로 공격을 모두 막아 차이가 식별되지 않으면 가림 추가 효과는 INCONCLUSIVE다. “더 안전함”으로 표시하지 않는다.
- O1 대 U1의 사전 최소 개선폭과 인간 통과 비열등 허용폭이 충족될 때만 추가 효과를 지지한다.
- 특정 가상 카메라 한 종류 차단을 일반 입력 신뢰성 증명으로 확대하지 않는다.

## 8. V4 — 정상 사용자가 실제로 완료할 수 있는가?

### V4-01 설계

- 사람과 공격자는 같은 평가 source, 길이, 제한시간, 관문, 임계값 규칙을 사용한다.
- 정상 참여자는 조건 순서를 균형 배정한다. 같은 사람이 같은 원동작의 무가림판을 먼저 보고 가림판을 풀지 않도록 한다.
- source의 조건 배정은 참여자 간 교차 회전하고, 같은 참여자 내에는 source를 재사용하지 않는다.
- 기기, 브라우저, 조명, 손 선택, 경험을 기록한다. 특정 집단의 열악한 성능을 전체 평균으로 숨기지 않는다.
- 참여자 모집·동의·촬영·보관·접근성·중단 절차를 실행 전 연구자가 확정한다.
- 원영상이 없는 과거 데이터로 사람의 지각 오류와 손 추적 오류를 완전히 구분했다고 주장하지 않는다.

탐색 기본안: 새 참여자 12명, 지원되는 U0/U1/O0/O1 네 조건을 각 1세션 수행.
각 세션에 겹치지 않는 source 2개를 사용해 참여자당 8개 source를 본다.
test source 12개에서 source·조건의 배정 횟수를 가능한 균등하게 배치한다.
조건 순서는 4조건 균형 순서표를 3회 반복한다.
12명은 feasibility pilot이며 확증·대표성 표본이 아니다. 보호 도구가 없으면 U0/O0만 실시하고 보호 효과는 미검증으로 남긴다.
P0/P1은 과제가 없어 사람 모방 성능 비교에 합치지 않고 별도 운영 기준으로 측정한다.

### V4-02 지표와 시간

- 주 지표: 첫 시도 L3 완료율. L3가 없으면 L2 완료율로 명칭을 바꾼다.
- 보조: 재시도 포함 완료율, 권한 거절, 포기, timeout, 검출 실패, 관문 실패, 점수 실패.
- 전체 경과시간 median/p90과 성공자만의 시간을 함께 보고한다. 실패자를 시간 분석에서 조용히 제거하지 않는다.
- 권한 요청·문제 보기·수행·서버 대기 시간을 구분한다.
- 기존 12.7초는 segment.duration 합이며 새 전체 UX 시간의 기준값으로 대체하지 않는다.
- SUS는 보조 사용성 지표다. 다른 코호트 간 평균 차이를 인과효과로 해석하지 않는다.
- 카메라/손을 사용할 수 없는 경우의 대체 경로 필요와 비용을 기록한다.

탐색 기본안: 한 시도 최대 60초, 첫 시도 주 분석, 추가 2회까지 재시도 보조 분석.
이는 연구 운영 제안이며 서비스의 허용 대기시간으로 추천하는 값이 아니다.
실행 전 사용 시나리오에 맞춰 고정하고 양 조건에 동일하게 적용한다.

### V4-03 판정

사전 정한 인간 완료율 하한, 조건 간 허용 감소폭, 전체 시간·이탈 상한을 모두 확인한다.
공격을 줄였어도 사람 실패/이탈 증가가 허용폭을 넘으면 실용성 조건은 실패다.
표본이 작아 허용폭 판단이 안 되면 INCONCLUSIVE로 보고하며, 편한 조건만 골라 전체 성공으로 선언하지 않는다.

## 9. V5 — 비용 비대칭과 구매자 경제성이 실제로 성립하는가?

### V5-01 공격 비용

- C_setup: 라이브러리 구축·모델 준비·사전 추론의 일회성 비용.
- C_attempt: 한 번의 문제 관측·검색·렌더·제출 비용.
- p_success: 동일 프로토콜에서 측정한 전체 성공률.
- N: 사전 작업을 재사용할 수 있는 시도 수.

평균 비용 민감도:
C_attempt_amortized(N) = C_setup / N + C_attempt
C_per_success(N) = C_attempt_amortized(N) / p_success

이 식은 같은 비용·성공확률을 가정한 비교용 근사다.
재시도 상관·캐시·차단 정책이 있으면 실제 반복 실험의 총비용/성공 건수를 우선 보고한다.
p_success=0이면 무한대 비용으로 주장하지 말고 관측 0건과 불확실성으로 표시한다.

- N=1, 10, 100, 1000, 10000을 민감도 시나리오로 제시한다. 실제 트래픽 추정치가 아니다.
- CPU 시간, 경과시간, 메모리, 전송량을 우선 측정한다. 검증하지 않은 클라우드 가격으로 돈을 환산하지 않는다.
- cold/warm 실행을 분리한다. 반복 측정 기본안은 각 설정 warm 5회와 cold 1회이며 실행 변동 측정이지 공격 독립 표본 증가가 아니다.
- 적응형 공격·평가 튜닝 인력 비용은 기록 가능 범위에서 별도 표기하며 추측치를 측정치로 합치지 않는다.

### V5-02 방어 비용

- 가림 생성, 사람 손 검출, 채점, 서버 검증, 입력 보호 SDK를 각각 계측한다.
- 가림 자체가 가볍다는 것과 전체 서비스가 싸다는 것을 구분한다.
- 지원 장치별 처리시간, CPU/메모리, 서버 요청·전송량, 실패 재시도 부담을 기록한다.
- 과금 API는 무료 한도와 상용 가격을 구분한다. 가격은 조회일·지역·단위와 공식 URL을 붙인다.
- 지금 범위에서는 유료 자원을 결제하지 않는다.

### V5-03 고객 관점

월간 순가치 = 감소한 공격 피해액 − 증가한 정상 사용자 이탈 손실 − 추가 운영·지원 비용 − 사용료.

- 감소한 공격 피해액은 총공격 건수가 아니라 실제 피해로 이어질 사건과 기대 피해를 사용한다.
- 기본값은 고객 제공/측정/가정 중 하나로 표시한다.
- 낙관·기준·비관 시나리오를 만들되 원화 수치를 임의로 확정하지 않는다.
- 유효한 입력이 없으면 계산 템플릿까지만 완료하고 수익성은 미확인이다.
- 가장 저렴한 공격과 현실적 재사용량에서도 방어 가치가 있는지 본다.
- GPU가 필요한 느린 공격 하나만 이긴 결과로 “공격 비용이 높다”고 결론 내리지 않는다.

## 10. V6 — 필요한 고객이 실제로 지불할 것인가?

### V6-01 조사 대상과 기록

기술 시험과 병행 가능한 시장 검증 계획이다. 이 문서는 연락·발송 권한을 부여하지 않는다.
공개 제품 조사 → 연구자가 승인한 인터뷰 → 범위/견적 검토 → 실제 계약 순으로 증거를 쌓는다.

후보군:
1. 봇 방어 제품사
2. 카메라 입력 보호·생존성 제품사
3. 카메라 기반 서비스를 만드는 개발사/운영사

탐색 목표는 각 군 2개 조직, 총 6개 조직의 유효 대화다.
이는 시장 전체를 추정하는 표본이 아니라 고객 가설을 버리거나 좁히는 운영 목표다.
무응답은 수요 없음과 구분하고 연락 가능성 문제로 기록한다.

비공개 customer_evidence에는 아래를 기록한다.

- customer_code, 담당 역할, 적용 업무, 문제 빈도와 근거, 현재 대체재
- 카메라/손동작/얼굴 사용 제약, 정상 사용자 이탈 허용 범위
- 외부 손 챌린지/입력 보호 통합 가능 여부
- 평가 담당자, 예산 책임자, 구매 일정, 평가 환경 제공 여부
- 원하는 납품물, 성공 기준, 예상 예산의 출처, 실제 제시한 견적
- 관심/평가 의사/예산 확인/계약/지급 중 어느 단계인지
- 거절 이유와 대체 요구, 연구자의 해석과 상대 발언의 분리

실명·연락처·고객 로그·미공개 사업정보는 공개 Git에 올리지 않는다.

### V6-02 인터뷰 질문

- 지금 어떤 자동화 때문에 어떤 손실/업무가 생기는가?
- 현재 해결책을 쓰면서도 남은 문제가 무엇인가?
- 어떤 사용자 행동 단계에 추가 확인을 넣을 수 있는가?
- 카메라와 손동작이 허용되는가? 얼굴 방식 대신 손이 필요한 이유는?
- 우리 기능 없이도 현재 입력 보호/다른 제품으로 해결 가능한가?
- 무엇을 얼마나 개선해야 도입할 이유가 생기는가?
- 고객 전용 연결·평가를 수행한다면 어떤 산출물에 예산을 쓸 수 있는가?
- 누가 도입을 결정하고 어떤 절차를 거치는가?

“아이디어가 좋은가?”라는 질문의 긍정 응답만 수요로 세지 않는다.

### V6-03 거래 검증

관심 < 구체적 사용처 < 담당자·환경 배정 < 범위·예산 합의 < 계약·지급을 구분한다.
무료 데모와 유료 맞춤 개발을 구분한다.
과제 계약안에는 적용 흐름 하나, 연결 범위, 비교 시험, 납품물, 검수 기준, 지급 시점,
상용 사용권과 연구용 평가권의 구분, 지원 범위를 명시한다.
기존 코드·데이터·권리의 이용 조건을 확인하지 않은 채 독점 양도나 소스 제공을 약속하지 않는다.
시장 검증을 명목으로 성능을 보증하거나 지원 범위를 무한정 늘리지 않는다.

### V6-04 판정

- 1개 조직의 실제 지급은 최초 거래 근거이지 반복 가능한 시장 검증 완료가 아니다.
- 견적·평가 의사만 있으면 purchase_intent이며 매출로 보고하지 않는다.
- 6개 유효 대화에서 적합한 사용처도 담당자도 없으면 대규모 제품 개발을 멈추고 고객군/용도를 재검토한다.
- 기술과 다른 구매 이유를 발견하면 변경된 고객 가설을 기록한다.
- 기업 접촉이 승인되지 않았으면 공개 조사·질문지·평가 계약 범위안까지만 완료한다.
- 실제 구매 증거가 없으면 수익화 가능성은 INCONCLUSIVE로 유지한다.

## 11. 통계·표본·해석 요구사항

- 모든 비율에 분자/분모와 분석 단위를 병기한다.
- 같은 source·같은 참여자의 반복을 독립으로 취급하지 않는다.
- source/참여자 군집을 유지한 구간 추정 또는 대응 분석을 사전에 선택한다.
- 군집 수가 작으면 CI가 불안정함을 표시하고 원본 단위 기술통계와 차이 범위를 우선 제시한다.
- 독립 시행을 가정한 0/n 상한으로 상관된 반복 프레임의 보안성을 증명하지 않는다.
- 보안 주 비교는 O1-U1 하나를 우선하고, 공격군별 결과와 최악의 공격을 전부 보고한다.
- 다수 후보를 test에서 골라 최고 결과만 발표하지 않는다.
- 표본 설계 문서에는 pilot 관측 분산/군집 구조, 최소 효과, 목표 정밀도 또는 검정력, 탈락 예상, 계산 코드를 포함한다.
- pilot 관측치를 확증 자료에 재사용할 경우 적응 설계를 사전 명시해야 하며, 그렇지 않으면 분리한다.

실행 전 threshold_contract 필수 항목:

| 항목 | 의미 | 확정 주체 |
|---|---|---|
| human_success_floor | 최소 정상 사용자 완료율 | 연구자 + 사용 시나리오 |
| human_noninferiority_margin | O1에서 허용할 완료율 감소폭 | 연구자/고객 |
| attack_success_ceiling | 공격군별 허용 전체 성공률 | 위협 모델/고객 |
| min_attack_reduction | O1 대 U1의 의미 있는 감소폭 | 연구자/고객 |
| latency_limit, abandonment_limit | 전체 시간·포기 허용 범위 | 고객 시나리오 |
| min_net_value | 유지할 최소 순가치와 기간 | 고객 경제성 |
| sample_plan | 독립 단위 수와 정밀도 근거 | 분석 담당자 검토 |

지금 이 표에 업계 기준인 것처럼 임의 숫자를 넣지 않는다.
확증 실행 전에 값·근거·고정 시점을 채운다.

## 13. 실행 순서, 역할 및 자율 진행

이 커밋은 명세와 별도 수학 모듈 개선 시작을 포함한다. 후속 실제 자료/시스템 실행 단계가 승인되면 그 범위 안에서는 아래 의존성을 따라 연속 진행한다.
이미 승인된 내부 작업마다 반복 확인을 요구하지 않는다.

1. V0 자료·코드·분모 연결 및 미확보 목록.
2. V1 기존 데이터 기반 채점 오답·회귀 계획 및 승인된 로컬 검증.
3. V2 기존 closed-set 진단. 신규 데이터가 준비되면 분할 고정 후 held-out.
4. V3 입력 보호 적합성 조사. 실제 도구가 있을 때만 통합 시험.
5. V4 승인된 참여자 pilot. V2/V3와 같은 조건·버전으로 대응.
6. V5 측정 기반 비용 계산.
7. V6 별도로 승인된 고객 검증. 기술 결과를 기다리는 동안 공개 조사·제안 범위 작성 가능.
8. 독립 검산 및 decision_report 작성.

역할은 작업 책임의 구분이며 자동 다중 에이전트 실행 명령이 아니다.

- 설계/분석: 프로토콜, 분할, 분석 단위·판정 기준.
- 구현/시험: 로깅, 분석기, 테스트 시스템, 회귀 검사.
- 검증: 핵심 지표의 별도 계산 경로, 누출·분모·해석 반증.
- 연구자: 목표/실행 범위, 참여자·고객 활동, 최종 의사결정.

필수 자원이 없으면 해당 항목만 BLOCKED로 두고 독립적으로 가능한 일을 계속한다.
승인 범위를 넘어 신규 모집·외부 연락·배포·유료 결제가 필요한 경우에만 그 종속 작업을 보류한다.
과거 자료의 불일치를 무한히 추적하지 않는다. 기존 주장에 영향이 없는 계보 공백은 한계로 남긴다.

## 14. 자동 점검과 인수 기준

문서/계획 단계:
- 모든 V0–V6 항목에 입력, 절차, 출력, 완료·실패·보류 기준이 있다.
- 이미 완료한 G3/G4와 새 제안을 구분한다.
- 임의 성능 수치를 입증된 결과로 제시하지 않는다.
- 기술적 가능성·사용성·경제성·구매 증거를 별도 판정한다.

구현 단계에서 필요한 검사:
1. source/capture_group 분할 교집합 검출.
2. L2 성공인데 L3 실패인 fixture를 전체 성공으로 세지 않음.
3. 결측/timeout/추출 실패를 숨겨 분모가 줄지 않음.
4. 입력 보호 미실행 null과 실패 false를 구분.
5. 잘못된 답이 기존판에서 통과한 회귀 사례를 보존.
6. 세션 중복·재시도·조건 순서를 정확히 집계.
7. token 재사용·만료·세션 불일치 차단을 통제 환경에서 검증.
8. setup 비용 재사용과 p=0 처리를 올바르게 계산.
9. 공개 산출물에 비공개 행/식별정보가 섞이지 않음.
10. 별도 계산 경로로 주 결과의 분자·분모와 표본 일부의 점수를 확인.

이번 커밋의 실제 검사 범위는 별도 채점 모듈의 합성 수학·분모·분할 검사다. 위 전체 시스템 인수 검사를 실행했다고 쓰지 않는다.

## 15. 최종 의사결정표

| 결과 조합 | 결론과 다음 행동 |
|---|---|
| 채점 취약 또는 저비용 공격이 목표 초과 | 현재 설계의 보안 제품화 중지, 원인 수정 범위를 한정하고 새 test 계획 |
| 보안 개선은 있으나 사람 부담이 허용폭 초과 | 적용 상황 제한 또는 UX 수정. 일반 CAPTCHA 대체 주장 보류 |
| 입력 보호만으로 같은 성능 | 가림의 추가 가치 미확인. 추가 비용을 정당화할 다른 근거 필요 |
| 기술·사용성은 만족, 구매 증거 없음 | 제품 개발 확대 보류. 고객 가설 검증 |
| 고객 관심만 있고 기술 미달 | 탐색 공동연구 논의 가능, 완성 보안 제품 판매 주장 금지 |
| 기술·사용성·경제성 만족 + 유료 평가 계약 | 제한된 공동개발 진행 가능. 일반 시장 성공으로 확대하지 않음 |
| 서로 다른 고객이 같은 핵심 모듈을 유료 사용 | 재사용 가능한 SDK/서비스 제품화 검토 |
| 핵심 입력/표본/도구 부족 | 판단 보류와 필요한 증거·비용 기록 |

decision_report는 긍정·부정 결과 모두 포함하며 다음을 한 문단씩 답한다.
“무엇이 확인됐나 / 무엇이 반박됐나 / 무엇이 아직 불명확한가 / 다음 투자로 무엇을 알 수 있나 /
그 증거가 나오지 않으면 어디서 멈추나.”
