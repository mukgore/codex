# 보완 실험 제안(사용자 검토 전 실행하지 않음)

여기서는 새 CAPTCHA를 설계하지 않는다. 현재 자료의 모순을 해소하거나 가장 큰 주장을 반박 가능한 방식으로 평가할 최소 실험만 제안한다. 모든 표본 크기, 성공률 목표, cutoff는 pilot/위험 기준에 근거해 별도 사전 결정해야 하며 지금 임의 수치를 정하지 않는다.

## F0 — 누락된 기존 증거 회수·재현성 복구 (우선 1)

**검증 질문:** 기존 4명 MediaPipe, 10명 A/B, 첫 6클립 HaMeR 수치가 분석 가능한 원자료와 같은 점수식에서 나오는가?

- **가설/반증 예측:** 가능한 원응답·로그를 원코드로 재계산하면 보고서 점수/p값과 일치한다. 점수 또는 연결 자료가 없으면 재현 불가 판정.
- **변경/고정:** 새 관찰 변인 없음. 보고서 수치와 원본 파일/노트북/실행 commit만 연결. 이미 없는 파일은 합성 생성하지 않음.
- **단위/분할:** 사람 참가자×조건×시도, model 입력 clip×condition. 누락된 사람별 A/B 쌍 하나라도 표시. cohort는 서로 병합하지 않음.
- **지표:** 원점수 delta, 계산 버전, 누락률, 제외 인원, p/효과크기 재현. 기존 짝 설계라면 참가자별 paired difference.
- **배제:** 중복 내보내기, 손상 레코드는 hash/파서 증거로만 구분; 점수가 낮다는 이유로 제외 금지.
- **결과 해석:** 일치 시 그 원래 표본·조건으로만 지지. 불일치 시 이전 집계 버전 차이 특정 전까지 결론 보류. 원자료 누락 시 재현 불가로 기록.
- **장비/참여자:** 기존 파일 회수만으로 충분할 수 있음. 신규 모집/실행 필요성이 생기면 이 실험 카드 사용자 승인 뒤 설계.
- **최소 산출:** commit+입력해시+설정이 있는 reproduction table, 개별 파일 공개 대신 합산 CSV/검증 로그.

## F1 — 같은 challenge에서 사람/공격자 전체 흐름 비교 (우선 2)

**검증 질문:** 현재 선택한 8개 동작·threshold에서 특정 공격이 전체 인증에 성공하는가, 그리고 사용자와 공격자에게 입력이 같은가?

- **반박 가능한 가설:** 고정된 평가 풀에서 공격자 흐름이 사람보다 낮은 시스템 통과율을 보일 수 있다. 점수 통과만 높고 관문/제출 흐름 통과가 낮으면 “전체 인증 성공”을 반박.
- **변경/고정:** challenge 영상/전환/프레임, 좌우손 변환, 38° gate, 전체 score/threshold, 재시도, 시간 제한을 고정. model에만 별도 fade를 주지 않고 사람이 본 픽셀 입력과 공격자가 사용하는 입력을 같게 하거나 입력 차이를 factor로 분리.
- **표본 단위/분할:** 독립 단위는 원본 gesture/clip 또는 독립 participant. 같은 clip에서 만든 방향/조합은 같은 split에 둔다. 개발 split에서 cutoff를 고정하고 held-out 원본에서 평가.
- **주 지표:** 성공/실패는 (i) 포인트 gate, (ii) score, (iii) 보호 action까지 세 단계 별도. 보조는 점수·첫 시도·재시도·전체 시간·감지율/관절오차.
- **공격 자원:** 사전 library, CPU/GPU, 모델 준비·추론시간, cache, 재시도·동시성 기록.
- **중단/제외:** 기술 로그 손실/카메라 권한 실패는 사용자 과제 수행 실패와 다르게 표기. 정당한 접근성 사유 참가자를 임의 삭제하지 않음.
- **해석:** 실패한 단계에 한정해 공격 저항을 지지. 실제 운영 시스템에 서버 검증이 없으면 online service security 결론 없음.
- **표본크기:** 18 사람·8 고정 clip은 소규모 탐색 자료. 확증 표본은 사전 지정 효과크기/불확실성 폭을 바탕으로 지도교사·사용자가 승인 후 산출.
- **최소 구현:** 기존 score runner와 기록 schema만 연결; 새로운 문제·UI는 없음.

## F2 — challenge 정보 누설 ablation (우선 3)

**검증 질문:** 정답 정보는 원 궤적/크기, 원 주변 노출, 보이는 영상·배경/파일 메타데이터, 저장 답 재사용 중 어디서 공격에 전달되는가?

- **예측:** 각 입력 채널을 하나씩 제거/마스킹하면 identifier 또는 replay 성공이 하락할 수 있다. 어느 채널도 결과에 영향이 없으면 그 채널이 원인이라는 주장을 반박.
- **고정/변경:** 동일 원본·참조 라이브러리·matching algorithm·score cutoff. A: circle center/radius trajectory only, B: circle 제거하고 나머지 공개 프레임, C: 경계 피부 bit만, D: 파일명/길이/전환 metadata만, E: 저장 답 재생만, F: 위 결합. 사전지식/사전계산 유무를 분리.
- **단위:** 원본 clip×시도. 원본 변형은 같은 개발/검증 쪽에만 둠.
- **지표:** top-1 식별/유일식별, 오답 replay score/gate, attack preparation time, query time. 16개 표본의 비율에는 불확실성 폭과 pair별 결과 병기.
- **제외:** 추출 실패를 조용히 제거하지 않고 challenge 실패로 포함/별도 분류.
- **해석:** visibility-bit 공격 수치를 circle-only attack으로 대신하지 않는다. 실제 사용자가 말한 원 중심·크기 공격은 별도 raw observation으로 재현해야 한다.
- **장비/참여자:** 저장 영상만 있으면 비인적 로컬 분석; 원 입력 동영상이 없어 현 자료로 pixel-only ablation 일부는 불가.

## F3 — 고정 평가식/일반화 검사 (우선 4)

**검증 질문:** 인간/HaMeR 점수 격차가 weight, E_max, 동일 8개 동작 선택에 의존하는가?

- **고정:** 개발 단계에서 score 정의·38° 관문·cutoff를 잠그고 신규 held-out 원본 clip에서 한 번 평가.
- **분할:** 같은 원본의 세션·프레임·미러·시간 변형은 전부 같은 split. 개인이 반복 수행하면 사람별 paired analysis.
- **주 지표:** 조건별 participant/clip 통과율과 95% 불확실성, 점수 분포·effect size. 반복된 HaMeR pair는 gesture source 단위 cluster 또는 descriptive only.
- **보조:** E_max 선택을 바꾸는 sensitivity plot은 투명하게 모두 표시; 최적 threshold를 test 결과 보고 골라내지 않음.
- **결과:** held-out에서 사람 통과율이 낮거나 공격 통과율이 높으면 해당 보안 목표는 실패로 채택 가능.
- **표본:** 원본 다양성·target effect size 근거를 확보한 후 사전 산출.

## F4 — 인지/사용성 기제 분리 (우선 5; 인적 승인·지도교사 절차 선행)

**검증 질문:** A/B 수행 차이가 가려진 시간 맥락 추론 때문인가, 입력량·기억·전환·운동/카메라 추적 부담 때문인가?

- 동일한 손 운동, challenge 수, 노출 프레임 총량 및 제한 시간을 맞추고 시간 순서를 참가자 간 counterbalance. 조건 자체가 프레임 수를 다르게 만드는 현재 설계의 혼입을 줄임.
- 사람이 본 정답 sequence/목표 관절, camera detection rate, 완료시간, 점수, 오류 종류를 별도 측정한다. 손 좌표 정답으로 사람 지각 오류와 운동 재현·tracker 오류를 구분.
- 같은 참가자의 paired condition difference로 분석. 한 참가자 반복 프레임을 새 표본으로 취급하지 않음.
- predictive-coding은 조작 가능한 이론적 예측과 대안 가설이 사전 정의되기 전까지 메커니즘 결론 대신 설계 동기/가설로 제한.
- 표본/동의·중단·접근성 기준은 학교 연구 정책과 지도교사 승인으로 결정. 현 단계에서 모집하지 않음.

## 승인 이후에만 고려할 사항

새 가림 방법/손-물체 CAPTCHA/영화 필름 입력, 좌표 그리기·관절 드래그 UI, 서비스·API·외부 호스팅은 위 결과를 사용자가 검토·승인한 뒤 새로운 실험 ID와 카드로 제안한다. 이번 1차 계획 문서에서는 후보 선택이나 구현을 진행하지 않았다.
