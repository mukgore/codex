## 2. 자세 관문과 기록 흐름

- **코드 확인:** 관절 각도는 landmark 삼중항의 두 벡터 내적을 이용한 `acos`로 계산하고 도 단위로 바꾼다. 15개 관절 삼중항의 절대 각도 차 평균이 자세 오차다 (`hand_captcha_prod.html`, 136–138, 305–318행).
- **코드 확인:** 각 landmark는 손목 좌표를 빼 원점 이동한 뒤 손목–중지 MCP(landmark 9) 거리로 나눈다 (`ppSingle`, 310–318행). 오차가 38도 **미만**인 상태가 200ms 이상 이어져야 통과한다. 각 검출 프레임의 오차가 기준 이상이거나 손이 검출되지 않으면 유지 타이머를 초기화한다 (130–133, 783–825행). 이는 한 번의 일치만으로 통과하는 조건이 아니다.
- **코드 확인:** 첫 목표 자세 통과 후 `beginNextTransition`에서 전환 기록을 시작한다. 동일 clip의 다음 keyframe으로 갈 때만 원본 영상을 시작 keyframe부터 재생하고, 목표 keyframe 시각보다 0.05초 앞에서 멈춘 뒤 그 프레임을 유지한다. 재생 오류 또는 제한시간 초과 시에도 영상 재생 상태를 끝내고 자세 matching으로 넘어간다. clip이 바뀌면 전환 영상 대신 목표 keyframe을 표시한다 (531–641행).
- **코드 확인:** 전환 기록은 영상 재생 중에도 프레임별로 쌓이며, 검출 실패 프레임은 null로 기록된다. 재생·페이드가 끝난 다음 목표 관문을 만족하면 구간 기록을 닫는다 (783–846, 644–661행). 관문은 challenge 흐름을 진행시키지만 최종 score는 별도로 계산되어 `captcha >= 0.25`일 때만 결과 화면의 점수 판정이 통과다 (133–135, 861–897행). 이 코드에는 서버 측 인증 성공이나 보호 자원 접근 허가의 증거가 없다.
- **코드 확인:** 평가용 `stop_on_fail=false`는 저장된 HaMeR 평가를 중간 관문 실패에서 중단하지 않고 계속 채점하는 설정이다. 사람용 브라우저는 매 keyframe 관문을 만족해야 다음 구간으로 진행한다. 그러므로 평가 notebook의 점수 통과를 실제 사용자 전체 challenge 통과로 바꿔 읽을 수 없다.
- **A/B 코드 확인:** A/B 버전은 동일한 38° 미만 관문을 쓰지만, 조건을 유지하는 시간 검사는 없다. 검출 프레임 하나에서 기준 미만이면 바로 다음 상태로 넘어간다 (A/B HTML, 168, 492–518행). 200ms hold는 나중의 `prod_v2_pool` 코드에 있는 조건이다.
- **A/B 코드 확인:** A/B에서는 keyframe 관문을 모두 진행한 뒤 각 조건의 score를 산출해 다음 조건 또는 비교 결과 화면으로 간다. `THRESHOLD=0.25` 상수는 선언되어 있지만 score 기준으로 trial 완료나 실제 인증을 허용하는 분기는 찾지 못했다 (A/B HTML, 169, 560–647행). 점수는 비교 측정치이며 실제 서비스 인증 결과와 동일시할 수 없다.

이 의사코드는 이후 `prod_v2_pool`의 200ms hold 흐름이다. A/B의 즉시 관문과 제시 차이는 아래에 별도로 정리했다.

```text
A/B 공통: 같은 3-action/keyframe 시퀀스와 무작위 조건 순서를 설정
A: 같은 action 내부 전환은 원본 영상 재생 후 정지, 다른 action은 목표 프레임만 표시
B: 전환 영상 없이 fade 후 목표 keyframe 정지 프레임 표시
양 조건: 38° 미만인 검출 프레임에서 즉시 관문 진행, 유지 시간 없음
B에서도 저장된 해당 원본 구간과 사용자 전환 궤적을 비교
```

`prod_v2_pool` 사람용 흐름의 간단한 표현:

```text
무작위 pool clip 2개 선택 → keyframe 자세 제시
첫 자세가 38° 미만으로 200ms 유지될 때까지 대기
각 전환의 사용자 프레임 기록 시작
같은 clip이면 원본 영상을 다음 자세 직전까지 재생하고 정지
다른 clip이면 목표 keyframe 이미지를 표시
목표 자세가 38° 미만으로 200ms 유지되면 구간 확정 후 다음 자세
모든 관문을 거친 뒤 별도 score 계산 → score >= 0.25 여부 표시
```

## 3. A/B 제시 방식

- **A/B 코드 확인:** A는 같은 동작(action)의 keyframe 사이에서만 기준 영상을 시작 keyframe 시각부터 재생하고 목표 시각보다 0.05초 앞에서 멈춘다. 마지막 표시 프레임을 canvas에 고정한 뒤 자세 관문을 확인한다. 서로 다른 action 사이에는 영상을 재생하지 않고 목표 keyframe만 표시한다 (A/B HTML, 339–384행).
- **A/B 코드 확인:** B는 전환 원본 영상을 재생하지 않는다. 화면을 잠시 fade 처리한 뒤 목표 keyframe의 정지 프레임을 표시한다 (385–401행). 따라서 “B는 동작 영상 전체 대신 정지 프레임 조건”으로 설명할 수 있다.
- **A/B 코드 확인:** A와 B는 `savedKeyframeSpec`을 재사용하므로 같은 손·동작·keyframe 시퀀스를 조건만 바꿔 두 번 수행한다 (283–299, 544–577행). 순서는 코드상 무작위다. B에서도 사용자 전환 궤적은 저장되며 원본 비교 구간은 출발 keyframe부터 도착 keyframe까지의 기준 궤적이다. action이 바뀌는 구간에서는 이전 action의 나머지부터 다음 action의 해당 keyframe까지를 이어 붙인다 (587–605행).
- **코드 확인:** A/B는 3개 action을 손에 따라 선택하고 참가자가 손을 직접 선택한다. 현재 `prod_v2_pool`은 pool에서 무작위 두 clip을 고르고 손 방향을 자동 판별하는 별도 흐름이다 (A/B HTML, 167행, 283–299행; production HTML, 397–429행).
- **A/B 코드 확인:** 목표 자세가 아직 맞지 않으면 안내 문구에 반올림한 각도 오차를 표시한다. `prod_v2_pool`은 mismatch 때 일반 안내 문구를 표시한다 (A/B HTML, 495–500행; production HTML, 821–825행).
- **판정:** 사람용 A/B 실험은 `ab_v2_3actions`; 이후 pool 시제품은 `prod_v2_pool`이다. A/B JSON 10건의 표식은 공개 A/B 파일 버전과 일치하지만 source hash가 없어 정확한 실행 revision만 미확인으로 남는다.

## 4. 가림 생성

- **코드 확인:** `0222_handtest1_AI.ipynb` 코드 셀 2에서 픽셀 좌표의 손목 `W`와 MCP 다섯 점(landmark 1, 5, 9, 13, 17)의 평균 `M`을 사용한다. `d = sqrt((Mx-Wx)^2 + (My-Wy)^2)`이며, 계수 `q`에 대해 원 중심은 `C = W + (q/2)(M-W)`, 반지름은 `int(q*d/2)`다. 중심 좌표 성분도 int로 변환한다. 지름은 반올림 전 `q*d`다.
- **코드 확인:** 셀 3의 계수는 level1_MCP 1.45, level2_PIP 1.75, level3_DIP 1.95다. 9번 랜드마크는 가림 원 크기 산정에서 다섯 MCP 평균의 일부일 뿐이고, 손목–9번 단독 거리는 정규화 기준이다.
- **코드 확인:** 검출된 프레임마다 중심·반지름을 갱신해 검은 원을 그린다. 검출 누락 시 직전 유효 위치를 재사용하며, 첫 검출 전에는 원을 그리지 않는다 (노트북 셀 2의 영상 생성 루프). 가림 계산은 x/y 픽셀 평면이며 landmark z를 쓰지 않는다.
- **저장 실행기록 확인:** 노트북 저장 출력은 3단계 결과 영상 및 결과 JSON 이름을 기록하고 오류 output은 보이지 않는다. 저장 기록은 이 코드의 과거 실행 흔적이며 7월 결과 폴더 전체의 생성 출처를 확정하지 않는다.
- **추론:** `circle_edge_attack/common.py`의 가림 함수와 노트북의 원 생성식이 실질적으로 일치해 재사용/공유 구현일 가능성이 있다. 직접적인 코드 복사 이력은 확인되지 않았다.

## 5. 정규화·리샘플링·점수

- **코드 확인:** 각 프레임에서 21개 관절의 x/y 각각에 손목 좌표를 빼고, 이어 손목–landmark 9 거리로 모든 좌표를 나눈다. z 및 실제 프레임 간격은 이 정규화·점수 계산에 사용되지 않는다 (`pp`, `hand_captcha_prod.html`, 843–848행).
- **코드 확인:** 기본 관절 오차 `mA`에서는 사용자 좌표 궤적을 기준 궤적 프레임 수에 맞춰 선형 보간하고 15개 관절각 절대오차 평균을 구한다. `mDA`는 기준 길이를 `N`이라 할 때 사용자 좌표열을 `round(1.2*N)`개로 보간한 뒤 길이 `N`의 모든 연속 창을 비교해 가장 작은 관절각 오차를 택한다. 예를 들어 기준 100프레임, 사용자 80프레임이면 `mA`에서 사용자 좌표열을 100개로, `mDA`에서는 120개로 만든 뒤 100개짜리 창 21개 중 최솟값을 쓴다. 관절각 시계열만 리샘플하는 것이 아니라 정규화된 21×2 좌표열을 보간한 뒤 각도를 계산한다.
- **코드 확인:** 이름에 DTW가 있으나 동적 시간 왜곡 누적경로가 아니다. 1.2배로 늘린 사용자 좌표열을 기준 길이 창으로 훑는 sliding-window minimum이다. `mAc`는 사용자 좌표를 기준 길이로 보간하고, 각 프레임 간 시간 간격으로 나누지 않은 2차 차분의 크기를 비교한다 (843–848행).
- **코드 확인:** 검출률은 기록된 모든 전환 프레임 수 `tF` 중 검출된 프레임 수 `dC`의 비율 `dR=dC/tF`이다. 결측 landmark 프레임은 좌표 오차 입력에서 제외되지만, 검출률이 각 하위 점수를 곱으로 낮춘다. 3개 미만 검출 프레임인 segment는 형상 비교 입력에서 생략되나 전체 기록 프레임 분모에는 남는다 (`computeScores`, 850–878행).
- **코드 확인:** 각 raw error는 해당 MX 상수(관절 46.9413°, sliding-window 관절 44.0014°, 좌표 2차 차분 0.1926)로 나눈 뒤 `dR * max(0, 1 - raw/MX)`로 반전·절단해 0–1 점수로 만든다. raw가 null이면 하위 점수는 0이다. 최종점수는 `0.38*sDA + 0.37*sAc + 0.25*sA`, 점수 통과 임계는 0.25 이상이다 (130–136, 848–897행).
- **A/B 코드 확인:** 공개 A/B HTML에도 같은 MX 상수·가중치와 `pp/rs/mA/mDA/mAc/es/computeScores` 계산 구조가 있다 (A/B HTML, 169–172, 579–605행). 다만 A/B에서는 최종 score를 성공 허가 조건으로 사용하지 않는다.
- **확인 범위:** 공개된 `ab_v2_3actions` 코드와 A/B JSON 버전 표식은 일치한다. 다른 이름의 과거 A/B 빌드가 있었는지, 개별 세션이 특정 Git commit에서 실행됐는지는 source hash 부재로 미확인이다.

## 6. 좌우 손 처리

- **코드 확인:** 전면 카메라 영상 표시를 좌우 반전하고, 같은 좌표 관례를 맞추기 위해 landmark x도 `1-x`로 변환해 표시·세션 기록·점수에 사용한다. handedness 판정은 반전 전 MediaPipe label을 좌우 swap 표에 넣는다 (`hand_captcha_prod.html`, 159–165, 727–809행).
- **코드 확인:** pool 영상의 기록 손과 사용자 손이 다르면 기준 영상 표시와 기준 landmark 데이터 모두 좌우 반전하도록 sequence 생성 로직에 명시되어 있다 (397–429행).
- **미확인:** 수집 당시 실제 브라우저/카메라별로 위 파일이 실행됐다는 로그는 없다. 따라서 코드상 좌우 처리와 모든 수집 세션의 실제 동작은 구분한다.

## 7. 추가 확인이 필요한 자료와 범위

1. 최종 pool 시제품 배포본 또는 실행 시 source/build hash, pool manifest revision, 브라우저 실행기록. 후보 HTML 둘 다 `prod_v2_pool`을 기록하므로 JSON 표식만으로 해당 파일을 구분할 수 없다.
2. 초기 n=4 원자료·생성 코드와 25개 파라미터 실험의 실행 로그/입력 자료. 25개 grid workbook 후보는 찾았지만 초기 n=4 실험과의 연결 근거는 없다.
3. HaMeR 평가 결과와 실제 실행 revision을 연결하는 source hash 또는 실행 manifest. `stop_on_fail=false` 평가 결과는 사람용 진행 흐름과 별도 보고한다.

사용자가 허용한 확장 범위에서 연구 폴더의 후보 파일을 메타데이터 중심으로 찾고, 관련성이 높은 A/B HTML·notebook·대응 workbook만 읽기 전용 확인했다. 현 프로젝트 밖에서 이어질 확인이 필요한 대상은 최종 pool 시제품의 배포 source/hash, 초기 n=4 원자료, 25개 grid의 실행 로그와 입력 자료다. workbook과 notebook은 이름과 구조가 맞지만 workbook은 정적 결과표여서 어떤 런타임/입력에서 만들어졌는지 직접 증명하지 않는다. 이 문서는 코드와 저장 흔적의 설명이며 특허 등록 가능성이나 실제 서비스 성능을 판단하지 않는다.

## 8. 추가 허가 범위에서 확인한 버전 연결

- **코드 확인:** 읽기 전용으로 확인한 연구 HTML 보관본 여러 개의 정규화 바이트 해시를 공개 `hand_captcha_ab.html` 경로의 GitHub 이력과 비교했다. A/B 보관본 일부는 2026-03-29의 `441feee176ff` 수정본과 정규화 후 일치하고, 나머지는 그 경로의 앞선 수정본들(예: `55859dd508b7`, `60a984accb77`, `29a2c1b13d01`)과 일치했다. 이는 보관본이 공개 A/B 코드 계열의 실제 과거 revision임을 뒷받침한다. 개별 JSON에는 hash가 없으므로 특정 기록을 특정 revision에 연결하지 않는다.
- **저장 실행기록 확인:** A/B JSON 기록의 가장 이른 timestamp는 공개 HTML 최신 변경 시각(2026-03-29 21:56 KST)보다 약 9분 뒤다. 기록 기간과 코드 이력은 시간상 양립한다. 시간 근접성만으로 해당 commit이 각 세션에서 실행되었다고 증명할 수는 없다.
- **코드 확인:** production HTML 후보들은 모두 `prod_v2_pool` 표식을 쓰지만 서로 다른 파일이다. 현재 프로젝트의 `hand_captcha_prod.html`과 `hand_captcha_prod_new.html`도 파일 크기·내용이 다르며 저장 설정이 다르다. 구 파일은 로컬 JSON 다운로드 흐름이 있고, 신 파일은 `SAVE_LOCAL_JSON=false`이며 업로드 주소도 비어 있다. 따라서 `prod_v2_pool`만으로 특정 JSON을 만든 파일을 식별할 수 없다.
- **저장 실행기록 확인:** 별도 2차 테스트 결과 묶음의 JSON 18건은 모두 `experimentInfo.version=prod_v2_pool`이다. 결과 기록에는 실행 HTML의 해시가 없어 위 후보 구분은 해결되지 않는다. 참가자별 값은 이 문서에 싣지 않았다.
- **코드 확인:** `CAPTCHA_25_combinations.ipynb` 코드에는 6개 action(`l1`–`l3`, `r1`–`r3`), 검출·추적 신뢰도 각각 5수준의 Cartesian grid, FPS 24, `static_image_mode=False`, `max_num_hands=1` 설정이 있다. 이는 25 설정 MediaPipe 공격/재인식 파이프라인의 강한 코드 후보이며, 여섯 동작 영상과 기준 landmark 입력을 사용하도록 작성되어 있다. 코드는 실행하지 않았고 저장 output도 확인하지 않았다.
- **코드 확인:** 해당 notebook의 `dtw_align`에는 동적 시간 왜곡 누적 경로 계산이 있다. 이는 브라우저 HTML의 `mDA`/`mAc`가 “DTW” 이름과 달리 sliding-window 최소 오차를 쓰는 것과 별도 알고리즘이다.
- **저장 실행기록 확인:** notebook이 지정하는 `captcha_25combo_results.xlsx`라는 동일 파일명이 같은 연구 자료 묶음에 있고, 수정일은 notebook 코드 파일시각보다 뒤다. workbook은 11개 시트로 구성되며 `6동작_평균`의 26행(헤더 포함), 여섯 동작별 상세 시트, 각 5×5 grid 축을 나타내는 아홉 개 6×6 히트맵 구조가 있다. 상세 시트는 150개 행을 포함한다. 수식은 없고 저장된 결과값으로 구성된다. 개별 셀 값은 공개 문서에 옮기지 않았다.
- **추론:** 동일한 산출 파일명, 25개 설정 요약 구조, 여섯 동작 축 및 시점은 notebook의 의도된 산출물이라는 강한 연결 근거다. 다만 workbook 안에 notebook revision/hash, 원 입력 hash, 실행 manifest가 확인되지 않아 그 결과가 이 notebook의 특정 revision 실행에서 만들어졌다고 확정할 수 없다.
- **미확인:** 초기 n=4 보고값과 이 25개 설정 grid의 특정 저장 결과 사이에 직접 연결되는 입력·실행 기록은 없다. 이 notebook/workbook을 n=4 사람 실험 원자료 또는 그 재현 결과라고 설명하면 안 된다.
