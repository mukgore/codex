# 특허명세서용 구현 사실 조사 — 2026-10-17

## 조사 범위와 근거 구분

이 문서는 코드가 구현하는 동작과 저장된 실행 흔적을 분리해 기록한다. 연구 프로그램은 실행하지 않았고, 영상·좌표·개별 점수·개인 식별자는 검토하거나 공개하지 않았다. 원본 코드와 노트북은 프로젝트의 별도 원본 폴더에 있으며 이 저장소에 복사하지 않았다. 아래 줄 번호는 조사 당시 파일 기준이다.

- **코드 확인:** 코드에 적힌 계산과 흐름. 실제 기기에서 그 코드가 실행되었다는 뜻은 아니다.
- **저장 실행기록 확인:** 노트북에 남은 output/execution metadata. 다시 실행해 검증한 결과가 아니다.
- **추론:** 여러 자료의 일치로 연결을 추정한 것이며 직접적인 생성 이력은 없다.
- **미확인:** 현재 허용된 자료로 결정할 수 없는 사항.

## 1. 버전과 실행 경로

- **코드 확인:** `hand_captcha_prod.html`과 `hand_captcha_prod_new.html` 모두 결과의 `experimentInfo.version`에 `prod_v2_pool`을 기록한다. 두 파일의 해당 사용자 흐름은 무작위로 pool clip 두 개를 선택하고 각 clip의 keyframe 자세를 구성한다 (`hand_captcha_prod.html`, 397–429, 902–923행; `hand_captcha_prod_new.html`, 대응 코드).
- **코드 확인:** 구 HTML은 결과 JSON을 다운로드하고 설문으로 이동하는 흐름을 갖는다 (902–945행). 새 HTML은 `SAVE_LOCAL_JSON=false`, 빈 `UPLOAD_URL`, 결과 화면 후 재시작 설정을 사용한다 (설정 138–146행, 결과 처리부). 두 파일은 `prod_v2_pool`이라는 같은 표식만 기록하므로 표식 하나로 어느 파일이 JSON을 생성했는지 구분할 수 없다.
- **저장 실행기록 확인:** 허용된 A/B JSON에서 A·B score와 순서에 해당하는 필드 및 `prod_v2_pool` 버전 표식을 확인했다. 다만 JSON에 소스 파일명, 소스 해시, 빌드 식별자는 없다.
- **추론:** A/B 원자료는 pool 시제품 계열에서 수집된 것으로 보이지만, 두 HTML 중 실제 생성 파일을 특정할 수 없다.
- **미확인:** 예비 실험, A/B 비교 화면, HaMeR 평가의 원래 진입점과 실제 브라우저 실행 파일 간 계보. A/B 폴더에는 원자료 JSON은 있으나 해당 제시 화면의 소스 코드는 확인되지 않았다. HaMeR 산출물은 별도 평가 노트북/결과 계열이므로 사람용 브라우저의 실행 증거로 취급하지 않는다.

## 2. 자세 관문과 기록 흐름

- **코드 확인:** 관절 각도는 landmark 삼중항의 두 벡터 내적을 이용한 `acos`로 계산하고 도 단위로 바꾼다. 15개 관절 삼중항의 절대 각도 차 평균이 자세 오차다 (`hand_captcha_prod.html`, 136–138, 305–318행).
- **코드 확인:** 각 landmark는 손목 좌표를 빼 원점 이동한 뒤 손목–중지 MCP(landmark 9) 거리로 나눈다 (`ppSingle`, 310–318행). 오차가 38도 **미만**인 상태가 200ms 이상 이어져야 통과한다. 각 검출 프레임의 오차가 기준 이상이거나 손이 검출되지 않으면 유지 타이머를 초기화한다 (130–133, 783–825행). 이는 한 번의 일치만으로 통과하는 조건이 아니다.
- **코드 확인:** 첫 목표 자세 통과 후 `beginNextTransition`에서 전환 기록을 시작한다. 동일 clip의 다음 keyframe으로 갈 때만 원본 영상을 시작 keyframe부터 재생하고, 목표 keyframe 시각보다 0.05초 앞에서 멈춘 뒤 그 프레임을 유지한다. 재생 오류 또는 제한시간 초과 시에도 영상 재생 상태를 끝내고 자세 matching으로 넘어간다. clip이 바뀌면 전환 영상 대신 목표 keyframe을 표시한다 (531–641행).
- **코드 확인:** 전환 기록은 영상 재생 중에도 프레임별로 쌓이며, 검출 실패 프레임은 null로 기록된다. 재생·페이드가 끝난 다음 목표 관문을 만족하면 구간 기록을 닫는다 (783–846, 644–661행). 관문은 challenge 흐름을 진행시키지만 최종 score는 별도로 계산되어 `captcha >= 0.25`일 때만 결과 화면의 점수 판정이 통과다 (133–135, 861–897행). 이 코드에는 서버 측 인증 성공이나 보호 자원 접근 허가의 증거가 없다.
- **코드 확인:** 평가용 `stop_on_fail=false`는 저장된 HaMeR 평가를 중간 관문 실패에서 중단하지 않고 계속 채점하는 설정이다. 사람용 브라우저는 매 keyframe 관문을 만족해야 다음 구간으로 진행한다. 그러므로 평가 notebook의 점수 통과를 실제 사용자 전체 challenge 통과로 바꿔 읽을 수 없다.

사람용 흐름의 간단한 표현:

```text
무작위 pool clip 2개 선택 → keyframe 자세 제시
첫 자세가 38° 미만으로 200ms 유지될 때까지 대기
각 전환의 사용자 프레임 기록 시작
같은 clip이면 원본 영상을 다음 자세 직전까지 재생하고 정지
다른 clip이면 목표 keyframe 이미지를 표시
목표 자세가 38° 미만으로 200ms 유지되면 구간 확정 후 다음 자세
모든 관문을 거친 뒤 별도 score 계산 → score >= 0.25 여부 표시
```

## 3. A/B 제시 방식

- **코드 확인:** pool 시제품은 무작위로 선택한 두 clip에서 keyframe을 추리고, 같은 clip 간 전환에는 원본 구간을 재생한다. 서로 다른 clip 간 전환에는 중간 원본 영상 구간을 재생하지 않고 목표 자세 프레임을 표시한다 (`hand_captcha_prod.html`, 397–429, 549–641행).
- **미확인:** 연구에서 A와 B로 명명한 두 제시 조건의 정확한 프레임 생략·표시 규칙 및 B의 사용자 전환 궤적과 비교한 원본 구간은 현재 확인한 소스에 없다. 따라서 이를 현재 pool 시제품 흐름과 동일시하면 안 된다.
- **판정:** 두 HTML 모두 `prod_v2_pool`을 기록하고 A/B 토글은 확인되지 않았다. 현재 사람용 시제품 흐름은 무작위 pool challenge로 확인되며, 실험 A/B 조건 중 어느 쪽과 동일한지는 미확인이다.

## 4. 가림 생성

- **코드 확인:** `0222_handtest1_AI.ipynb` 코드 셀 2에서 픽셀 좌표의 손목 `W`와 MCP 다섯 점(landmark 1, 5, 9, 13, 17)의 평균 `M`을 사용한다. `d = sqrt((Mx-Wx)^2 + (My-Wy)^2)`이며, 계수 `q`에 대해 원 중심은 `C = W + (q/2)(M-W)`, 반지름은 `int(q*d/2)`다. 중심 좌표 성분도 int로 변환한다. 지름은 반올림 전 `q*d`다.
- **코드 확인:** 셀 3의 계수는 level1_MCP 1.45, level2_PIP 1.75, level3_DIP 1.95다. 9번 랜드마크는 가림 원 크기 산정에서 다섯 MCP 평균의 일부일 뿐이고, 손목–9번 단독 거리는 정규화 기준이다.
- **코드 확인:** 검출된 프레임마다 중심·반지름을 갱신해 검은 원을 그린다. 검출 누락 시 직전 유효 위치를 재사용하며, 첫 검출 전에는 원을 그리지 않는다 (노트북 셀 2의 영상 생성 루프). 가림 계산은 x/y 픽셀 평면이며 landmark z를 쓰지 않는다.
- **저장 실행기록 확인:** 노트북 저장 출력은 3단계 결과 영상 및 결과 JSON 이름을 기록하고 오류 output은 보이지 않는다. 저장 기록은 이 코드의 과거 실행 흔적이며 7월 결과 폴더 전체의 생성 출처를 확정하지 않는다.
- **추론:** `circle_edge_attack/common.py`의 가림 함수와 노트북의 원 생성식이 실질적으로 일치해 재사용/공유 구현일 가능성이 있다. 직접적인 코드 복사 이력은 확인되지 않았다.

## 5. 정규화·리샘플링·점수

- **코드 확인:** 각 프레임에서 21개 관절의 x/y 각각에 손목 좌표를 빼고, 이어 손목–landmark 9 거리로 모든 좌표를 나눈다. z 및 실제 프레임 간격은 이 정규화·점수 계산에 사용되지 않는다 (`pp`, `hand_captcha_prod.html`, 843–848행).
- **코드 확인:** 기본 관절 오차 `mA`에서는 사용자 좌표 궤적을 기준 궤적 프레임 수에 맞춰 선형 보간하고 15개 관절각 절대오차 평균을 구한다. `mDA`는 기준 길이를 `N`이라 할 때 사용자 좌표열을 `round(1.2*N)`개로 보간한 뒤 길이 `N`의 모든 연속 창을 비교해 가장 작은 관절각 오차를 택한다. 예를 들어 기준 100프레임, 사용자 80프레임이면 `mA`에서 사용자 좌표열을 100개로, `mDA`에서는 120개로 만든 뒤 100개짜리 창 21개 중 최솟값을 쓴다. 관절각 시계열만 리샘플하는 것이 아니라 정규화된 21×2 좌표열을 보간한 뒤 각도를 계산한다.
- **코드 확인:** 이름에 DTW가 있으나 동적 시간 왜곡 누적경로가 아니다. 1.2배로 늘린 사용자 좌표열을 기준 길이 창으로 훑는 sliding-window minimum이다. `mAc`는 사용자 좌표를 기준 길이로 보간하고, 각 프레임 간 시간 간격으로 나누지 않은 2차 차분의 크기를 비교한다 (843–848행).
- **코드 확인:** 검출률은 기록된 모든 전환 프레임 수 `tF` 중 검출된 프레임 수 `dC`의 비율 `dR=dC/tF`이다. 결측 landmark 프레임은 좌표 오차 입력에서 제외되지만, 검출률이 각 하위 점수를 곱으로 낮춘다. 3개 미만 검출 프레임인 segment는 형상 비교 입력에서 생략되나 전체 기록 프레임 분모에는 남는다 (`computeScores`, 850–878행).
- **코드 확인:** 각 raw error는 해당 MX 상수(관절 46.9413°, sliding-window 관절 44.0014°, 좌표 2차 차분 0.1926)로 나눈 뒤 `dR * max(0, 1 - raw/MX)`로 반전·절단해 0–1 점수로 만든다. raw가 null이면 하위 점수는 0이다. 최종점수는 `0.38*sDA + 0.37*sAc + 0.25*sA`, 점수 통과 임계는 0.25 이상이다 (130–136, 848–897행).
- **미확인:** 이 점수식이 모든 과거 A/B 버전에서 동일했는지, 특정 JSON을 어느 HTML 파일이 실제 생성했는지는 소스 해시가 없어 확정할 수 없다.

## 6. 좌우 손 처리

- **코드 확인:** 전면 카메라 영상 표시를 좌우 반전하고, 같은 좌표 관례를 맞추기 위해 landmark x도 `1-x`로 변환해 표시·세션 기록·점수에 사용한다. handedness 판정은 반전 전 MediaPipe label을 좌우 swap 표에 넣는다 (`hand_captcha_prod.html`, 159–165, 727–809행).
- **코드 확인:** pool 영상의 기록 손과 사용자 손이 다르면 기준 영상 표시와 기준 landmark 데이터 모두 좌우 반전하도록 sequence 생성 로직에 명시되어 있다 (397–429행).
- **미확인:** 수집 당시 실제 브라우저/카메라별로 위 파일이 실행됐다는 로그는 없다. 따라서 코드상 좌우 처리와 모든 수집 세션의 실제 동작은 구분한다.

## 7. 추가 확인이 필요한 자료와 범위

1. A/B 조건별 화면 제시를 구현한 원 HTML/JavaScript와 조건 배정·실행 설정. 이 자료가 있어야 A/B의 실제 표시 구간과 JSON 생성 경로를 특정할 수 있다.
2. 최종 시제품 배포본 또는 실행 시 소스/build hash, pool manifest 버전, 브라우저 실행기록. 두 파일이 같은 `prod_v2_pool` 표식을 쓰므로 JSON 버전만으로 특정할 수 없다.
3. 초기 n=4 및 25개 파라미터 실험 설정·생성 코드·대응 데이터. 현재 발견된 여섯 MediaPipe 결과 쌍을 그 실험과 같은 것으로 확정할 근거가 없다.
4. 사람용 관문과 평가 코드 설정을 연결하는 실험 기록. `stop_on_fail=false` 평가 결과는 사람용 진행 흐름과 별도 보고한다.

현재 PC 밖 검색이나 미승인 폴더 탐색은 수행하지 않았다. 이 문서는 코드와 저장 흔적의 설명이며 특허 등록 가능성이나 실제 서비스 성능을 판단하지 않는다.
